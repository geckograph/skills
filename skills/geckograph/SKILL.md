# GeckoGraph

## First run

GeckoGraph turns a web app into tools an AI agent can use: it scans the running app into a graph of its features and the API calls behind them, and serves them to the app's users through a chat widget and MCP. The `geckograph` CLI links this repo to it and keeps the graph in step with the code. **Ask before you set up.** Setup installs the CLI and writes files into the person's repo, so do none of it until they say yes, even when their message asks for setup. Reading first is fine: this page, the repo, `geckograph version` and `geckograph setup_status`. Your first reply: one or two lines on what GeckoGraph is, then what Setup will do and one question, in this shape:

> Setup will: 1) install the GeckoGraph CLI (skipped if you have it), 2) sign you in to GeckoGraph (you open one link), 3) run `geckograph init`, which writes `geckograph.yml`, the `.geckograph` link file, the GeckoGraph skill and a GeckoGraph block in `CLAUDE.md` or `AGENTS.md` in this repo, and in GeckoGraph sets up the environment you pick and the app's widget (default settings) when it has none; when GeckoGraph sees the same routes under two addresses, Setup may merge their duplicate lines. Nothing is committed without your OK. OK to start?

Then wait for their answer. On yes, run Setup below yourself, in order, the CLI install too. **With no specific change to make, setup is the whole task.** Run Setup, including its repair check. Do not explore, scan or map the app's API. Whenever you ask the person to run a command, give the complete command with the folder: for one that keeps running, such as `geckograph dev`, "Open a new terminal and run: cd "<this repo's absolute path>" then geckograph dev, and leave it running", with the real path filled in; for a short one, in Claude Code, the `!` form, which runs in this folder.

## Setup

1. If `geckograph` is not on PATH, install it yourself. macOS and Linux: `curl -fsSL https://app.geckograph.com/cli/install.sh | bash`. Windows: `powershell -NoProfile -Command "irm https://app.geckograph.com/cli/install.ps1 | iex"` (it checks the download against the published `SHA256SUMS`; the release is not signed). If your tool permissions refuse the install, do not retry it or work around it: in one short line, ask the person to run it themselves (in Claude Code, by typing it in this chat with the `!` prefix: `! curl -fsSL https://app.geckograph.com/cli/install.sh | bash`, or on Windows `! powershell -NoProfile -Command "irm https://app.geckograph.com/cli/install.ps1 | iex"`), and wait until they say it is installed. A shell started before the install may not find it on PATH: run it by the path the installer printed (`~/.geckograph/bin/geckograph`, `geckograph.exe` on Windows, unless it named another folder).
2. Whenever a command prints `A newer GeckoGraph CLI is available`, run `geckograph update`, then run the command again. A fresh install is already current.
3. If a command says to log in, run `geckograph login --no-browser` in the background. It prints a sign-in URL whether or not a browser opens: give that URL to the person to open on any device, and wait until it prints `Logged in to GeckoGraph.` (the link expires in 10 minutes). Never sign in for them. If your tool permissions refuse it, ask the person to run `! geckograph login` themselves.
4. From the repo root, run `geckograph init`. It links the app, writes `geckograph.yml`, installs this skill into the repo, and writes a GeckoGraph block into `CLAUDE.md` or `AGENTS.md`. If it lists several apps, ask the person which one this repo is, then run `geckograph init --app <slug>`. It says which version it used and the address that version was scanned from; tell the person, and if they want another version run `geckograph init --version <version>`. When it asks which environment that address is, ask the person about their site, in these words: "Your app was scanned from <address>. Is that your test site or the site your customers use? (GeckoGraph keeps separate settings for each copy of your site, like test and live, so you can try things before customers see them.)" Test site: run `geckograph init --version <version> --env staging` (recommended for a first setup: nothing customers see changes). The site customers use: confirm once more ("Customers will see what GeckoGraph sets up there. Set up Live?"), then run `geckograph init --version <version> --env live --confirm-live`. Another copy they name (init lists the ones the app has, such as Development): run `geckograph init --version <version> --env <name>`. Init creates that environment on that version. Then write `surfaces:`, the front ends the graph covers: find the folders whose client code calls the routes init imported, propose them to the person ("The scan covers <UI>; its code is in <folders>. Is there more code for that UI?"), and write each as `- name: <UI>` with `paths: [<folders>]` once they agree. Covering another UI later is the person's call: they add a surface and scan that UI. When init prints a `mounts:` proposal, first tell the person in plain words what it found and what you will do, such as "GeckoGraph found 12 routes that appear under two addresses (/api/… and /v2/api/…). If they are the same API, I'll keep one line for each. I'll check your routing to confirm." Then check it against the app's route configuration; when the code does not settle it, ask the person ("Are /api/… and /v2/api/… the same API?") instead of guessing. If it makes one route of two routes the app keeps apart, do not run it: tell the person it is wrong. Otherwise run `geckograph contract mounts --yes`: it writes the proposal and keeps one imported line per route the proposal makes one, and the next relearn retires the other tool. When a feature uses the tool it would retire, relearn retires neither and names the features of each: ask the person which stays. Never add it by hand.
5. Run `geckograph setup_status` (init prints the same list at its end) and go through its open steps with the person, in order, starting with the one marked next. For Add the chat widget, or set up MCP, ask the person the plain choice it prints: yes, install the widget, or no, only use MCP. On yes, run `geckograph setup_status --widget yes`, then Ask the person which apps and pages get the widget, then set it up (see The widget). On no, run `geckograph setup_status --widget no`. With the widget, setup is not done until it is seen working: build and start the app the way the repo's own docs say (or ask the person to), open the page or ask the person to, and confirm the chat appears; if you cannot, say so as the one open item. An optional step never blocks setup: offer it once, with the reason it prints. A step done in the dashboard (turning MCP on, MCP branding, linking the repo, going live) is the person's: give them the page it prints, never do it for them.
6. Show the person what init and you wrote (`git status`) and commit it only after they agree. Never commit `.geckograph.local`; git ignores it.
7. Check what needs repair, on the environment init set up or named: run `geckograph list_validation_failures --env <it>` and `geckograph list_scan_flags --env <it>` (when init could not create one, it says to use `--version <version>` instead, which only reads). Count them only: do not open, investigate or repair any until the person asks. An empty list is not "all clear" when it says features were never validated or are not proven: pass those counts on, and say "all clear" only when it says every feature was validated. Then end with this report, short and in plain words: never a config key (`mounts:`, `surfaces:`) or an internal component name to the person; describe the thing instead ("your API appears at two addresses", "which part of your app the scan covers"). **Done**: a few lines on what Setup did and wrote, and whether it was committed. **Yours to do**: only what the person must do now, such as opening a sign-in link or reviewing and publishing a draft (its version, how many fixes, and its dashboard link); never going-live steps (production, MCP on production) or deploy-time ones (widget keys for deployed environments). Optional steps stay on the checklist, not in the report. **Decisions**: one at a time, each with your recommended answer and what happens when they are unsure ("Are /app/orders and /orders the same API? If you're not sure, say no: nothing breaks."); ask the next only after the answer. **To repair**: once the decisions are answered, the counts above. Propose no other work. End with one question. With something to repair, offer it, such as "4 features fail validation and 2 aren't proven yet. Want me to repair them now? The fixes go into a draft you review before publishing." (the counts the dashboard's Fix failing features step shows; add the rescan flags when there are any) (see Repair a failing feature, or a rescan flag). With nothing to repair, "Everything validated. What do you want to change?", or, when features were never validated, say so and ask what they want to change. Start no repair until the person says yes. Then stop.

## How GeckoGraph works

- GeckoGraph holds a graph of this app's features and the actions (tools) an AI agent calls on the app's API. The app's users reach it through chat, the website widget and MCP. An app that serves its end users through MCP builds its part of their sign-in (the session bridge) from the `geckograph-mcp-auth` skill, which `geckograph init` writes beside this one (outside a repo, `npx skills add geckograph/skills` adds both), and check it with `geckograph mcp auth check --app <slug> --env <environment>`.
- The graph comes from GeckoGraph's scan of the running app, which the person runs in the GeckoGraph dashboard. You never build it, and never write lines for what it already holds.
- `geckograph.yml` in this repo lists the app's routes. `geckograph init` writes the ones GeckoGraph already knows as `source: dashboard` lines. After that, a change that adds, changes or removes a route edits its line in the same commit. That is the only time you write a line. A line is written only for a route that code in a front end listed under `surfaces:` calls: a route only another UI calls, or no UI calls yet, gets no line, even when the UI will call it later.
- Shared environments (production, staging, and so on) give each page the version for the tools number its build carries, so deploying the code with its committed number is what ships a release there, and an environment that follows the code moves with each build on its own. Holding, resuming, approving and rolling back are a person's acts in the GeckoGraph dashboard; no command, CI step or API key does them. Each is Following, Approval or Held: `environments.md` beside this skill says what each means and where the person clicks. Your personal environment is yours: `geckograph dev` and `geckograph relearn` change only it.

## Guardrails

- Use only the `geckograph` commands this skill lists. The CLI reads the API address and key that `geckograph login` saved. Do not pass `--api` or `--api-key`.
- Never read `~/.config/geckograph/credentials.json` or any other credential or token file.
- Never call the GeckoGraph API directly, with `curl` or anything else. Never inspect the CLI binary, with `strings` or anything else.
- If a command is missing, run `geckograph update` and try again. If it is still missing, or a command fails, report it. Do not work around it.
- Never pass `--yes` to `geckograph contract pull` unless the person asked for it. Never pass `--yes` to `geckograph rescan` unless the person said yes to that run. `geckograph validate` on the test account a person authorized for the tenant sends real writes without asking again: say so in one line ("Validating with real writes as the test account, which is authorized for this tenant."); on any other sign-in it runs reads only.
- Never regenerate `geckograph.yml`. Edit your own `source: code` lines in it by hand. Never use `geckograph scan` to create or refresh `geckograph.yml`. Scan only prints what the walker sees.
- Never put secrets, tokens, cookies, or header values in `geckograph.yml`. Never write a catch-all `/api/trpc` line.
- Never try to hold, approve or roll back an environment: a person does that in the dashboard. The pull request is the last step here.

## The widget

The widget is GeckoGraph's chat on the app's own pages: one script tag that loads `geckograph-embed.min.js` through the app's relay, which `geckograph widget_config` prints. The tag names no GeckoGraph address, so the same committed tag works on your machine and on every deployed environment; which GeckoGraph answers is the relay's setting. A repo can hold many apps and pages, and only the person knows which should have it. **Ask the person which apps and pages should get the widget; do not guess.** Propose the pages of the surfaces `geckograph.yml` lists; the person decides. For each app they choose, run `geckograph widget_config --dir <app folder>` on the folder of the app whose pages get the tag (when that is a bundled front end, it also sets up the relay in the server app that serves it, or names the folder to run it on; never write the relay's addresses yourself), then add the snippet in the setup commit to the entry pages they named (layout, master page or `index.html`): the tag it prints, exactly, with each `{{…}}` or `%…%` rendered from the setting it names. Never write the tag yourself or drop an attribute: without `data-base-url` and `data-discovery-url` the widget reaches no GeckoGraph server.

- **Every widget needs the relay and a sign-in hand-off; never conclude that it needs neither.** GeckoGraph's chat does not answer a page on another origin, so the tag points at the app's own `/api/geckograph`: copy the relay for its stack from `relay/` beside this skill (`aspnetcore`, `aspnet-framework`, `nextjs`) into the app in the setup commit. Then find how the app's own API calls send the signed-in user's session (read its HTTP client or interceptor), and do the one that matches. A cookie (HttpOnly or not): the relay passes the page's cookies when a chat starts, and nothing more is needed. A header the page builds from a value JavaScript can read (local storage, a readable cookie): also call `window.GeckoGraph.setAuth({ token: <that value> })` once the bundle loads and whenever the value changes.
- `data-env-key` names one environment: your personal one on your machine, Staging's or Live's once deployed. `data-dev-token` is the developer's own, from their sign-in: it lasts 12 hours and `geckograph dev` renews it while it runs, only works on a local page, and is never committed. A server-rendered page renders it from the app setting; a bundled front end (Vite, Create React App, webpack) gets no `data-dev-token` at all: a build would keep an expired token, so the relay in the server app attaches the current one to each call, on the developer's machine only. When the environment follows the code, also add `data-build="…"` with the commit the build came from (the pipeline stamps `$(Build.SourceVersion)` or `GITHUB_SHA`); no `%VITE_GIT_SHA%` on a stack that is not Vite.
- `data-tools` is the tools number: which tools this build of the app was made with, so every page gets the graph tested with its own code, during a rollout or after a rollback too; a page without it is served tools 0, and only `geckograph release` issues a new one. Tools numbers and releases are your steps: never explain them to the person, who is only told that the widget is installed.
- When you change tools (a route and its line in `geckograph.yml`), run `geckograph relearn` and test, then `geckograph release --base <the number the app's config holds now, 0 if none>`; it prints the new number (`--json` gives `toolsNumber`) and edits no file. Put that number in the app's committed configuration, under the name the tag reads (`widget_config` prints it), in the form the stack uses for build-time settings that ship with the code (never a local or git-ignored file, an environment variable set on one machine, or a value a pipeline injects), make the embed tag render it as `data-tools`, never a literal, and commit it with the code and the `geckograph.yml` change it was released for. Deploying that build is what ships the release to an environment's pages: there is no dashboard step for it, except that with Approval on, an internal environment waits until a person approves it. With no release yet, the number is 0. When two branches both released, the number conflicts on merge: run `geckograph release` once on the merged code and commit the new number. To check later what a release shipped (the tools it added, retired with the reason, and updated, and the features it hid or added), run `geckograph show_release <n>`; never send the person to the dashboard for it.
- Before each commit and before `geckograph release`, run `geckograph check --tools <the number the app's config holds now, 0 if none>`. It reads `geckograph.yml`, the tools number and `data-tools`, and edits no file. Exit 0: passed. Exit 1: fix each problem it lists (each names its line or file), then run it again. Exit 6: `geckograph.yml` changed since that number was released: run `geckograph release --base <that number>`, put the number it prints in the config, commit it with the yml, and run `geckograph check` again.
- The values come from untracked local config, never from a committed file. `geckograph dev` keeps your personal environment's key and dev token in `.geckograph.local`; `geckograph widget_config --dir <app folder>` writes them into that app's local config git ignores (`.env.development.local` for a Vite or Create React App build, which a production build never reads; `.env.local` for Next.js; `appsettings.Local.json`; `Web.Local.config`) and prints the names it used and what the app still needs: on .NET Framework add `file="Web.Local.config"` to Web.config's `<appSettings>`; on ASP.NET Core load `appsettings.Local.json` as an optional source. When git does not ignore that file it adds it to this clone's `.git/info/exclude`, never to a committed file, and it refuses a file git tracks. A deploy sets Staging's and Live's key. Never put a key or token in a committed file. For Staging's and Live's keys, run `geckograph widget_key --env staging` and `geckograph widget_key --env live` (add `--json` for a script), and put each key into that deploy's app setting or pipeline variable, or tell the person where to put them when you cannot reach the deploy config. A widget key is publishable (it is in the page) and works only from its environment's allowed domains.
- Each value comes from configuration in the stack's own form, never a literal. A server-rendered page renders the app setting: `process.env` for Node, `GeckoGraph:EnvKey` and `GeckoGraph:DevToken` in ASP.NET Core, `GeckoGraphEnvKey` and `GeckoGraphDevToken` in `ConfigurationManager.AppSettings` on .NET Framework. A bundled app reads a build variable (`import.meta.env.VITE_GECKOGRAPH_ENV_KEY`), for the key and tools number only. A static page has neither: add what fills the values (a build step or a small server route) and tell the person what you added.

## geckograph.yml

One entry per procedure the client calls. The file is the complete list: add, change or delete lines; never rewrite it with only the lines you touched. Relearn retires each action it built from a line that left the file (see Remove a feature).

```yaml
version: 1
contracts:
  - method: POST
    path: /api/invoices/:id/archive
    name: archive_invoice
    description: Archives a sent or paid invoice so it leaves the open list. Drafts cannot be archived.
    request:
      reason: string?
    response:
      archived: boolean
    notes:
      request:
        reason: Shown to the customer on the archived invoice.
  - method: POST
    path: /api/trpc/invoices.archive
    binding: trpc
    request:
      id: string
```

- `method` is `GET`, `POST`, `PUT`, `PATCH`, or `DELETE`. `path` is relative and starts with `/`; a path parameter is `:name`. Relearn refuses a path with a host.
- `request` lists the fields the call sends: the JSON body for POST, PUT and PATCH, the query string for GET and DELETE. `response` lists the fields it returns. Types are `string`, `number`, `boolean`, `object`, `array`; `?` marks an optional field. One level deep.
- `name` (optional, snake_case) names the action relearn creates. If it is not snake_case or already taken, relearn keeps the generated name and says why.
- `binding: trpc`: one line per procedure, `/api/trpc/<router>.<procedure>`, never the catch-all `/api/trpc/[trpc]`. POST sends the input object as the body, GET sends it as `?input=<JSON>`. If the app's tRPC server uses `transformer: superjson`, the input goes as `{"json": …}`: relearn reads that from the code, or write `transformer: superjson` on the line (`none` for plain). If the app's own tRPC calls are batched, relearn does not create the line and says why.
- `binding: graphql`: one line per endpoint, usually `POST /graphql` with request `query: string`, `variables: object?`, `operationName: string?`. Lines are keyed by method and path (`operation:` is only a label), so do not add a line per operation or per field.
- `source: code` is the default and marks your lines. `source: dashboard` lines were imported by `geckograph init` from the graph GeckoGraph already has. Never edit them. Delete one only when your change removes its route from the app (Remove a feature). Only `geckograph contract pull` refreshes them, and only when the person asks.
- `ignore:` (optional, after `contracts:`) lists routes on disk that are not tools, one plain string each: `- POST /api/webhooks/stripe`. Relearn never makes them actions, also when the route is called through the dev tunnel. The GeckoGraph widget relay route is always ignored and needs no entry. `surfaces:` (optional, top level) lists the front ends the graph covers, each `- name: <UI>` with `paths: [<code folders>]`; `geckograph check` notes a file that has code lines and lists none. `mounts:` (optional, top level, `[/prefix, …]`) lists the path prefixes the API is served under, and `caseInsensitive: true` says the server ignores case. A route is then its method plus its path after any mount: relearn, `geckograph check` and `contract pull` treat one route seen under two URLs as one line, and a code line on a route Live already serves matches its imported line under any mount. Write a new code line's path under the mount most of the surface's imported lines use: that is the URL its tool calls.
- `description` (optional, one line) says what the call does and when a person would use it, in their words, from the code you just wrote. `notes:` (optional) holds one note per field, under `request:` or `response:`: what the field means, and an allowed value or a rule only when the code enforces it. Write both for every code line you add or change; a line without them gets a thin tool. Never on a `source: dashboard` line.
- No guardrails, permissions, examples, or GeckoGraph ids. **Auth and permissions.** Never put tokens, cookies, API keys, or literal header values in `geckograph.yml`. Relearn copies auth and CSRF headers from an existing action on the same origin, as placeholders only. To build or change the app's permissions endpoint (the Permissions hook), read `permissions.md` beside this skill and follow it; when you add or change a route and the app has that endpoint, update its answer for the route in the same change.

## The loop

`geckograph dev` holds the tunnel from your personal environment to the app's local server (default `localhost:3000`) while you work; relearn, and validate on the personal environment, need it. Run it yourself, from the repo: `geckograph dev --start --local <host:port>` starts it in the background, owned by the CLI, and returns. Confirm with `geckograph dev --status`, then tell the person it is running and that `geckograph dev --stop` stops it. Before relearn or validate, run `geckograph dev --status` and start it when it is not running: `--start` reuses the one already running, so never start a second. The status names the checkout and local app it serves, and whether its tunnel is online: when the checkout or local app is not this one, run `geckograph dev --stop` and start it here; while the tunnel is connecting, wait and check again. If your tool permissions refuse it, give the person the one complete command with this repo's absolute path (see First run). When a chat or relearn says the dev environment is offline, run `geckograph dev --status` and start it again.

### Add a feature
1. Run `geckograph list_features --json` and use the area that fits the request instead of creating one. Relearn files the feature under the area the line's path names (`/api/trpc/invoices.archive` -> Invoices), so put the route under that area's resource.
2. Implement the procedure and add its line to `geckograph.yml` by hand, in the same change.
3. Rebuild and restart the running app the way this repo's own docs say (its `CLAUDE.md`, `AGENTS.md` or README). Relearn calls the route through the `geckograph dev` tunnel, so the running app must include the change. When relearn says a route is missing or answers 404, check first that the running app was rebuilt.
4. With `geckograph dev` running, run `geckograph relearn`. Then validate the new feature on your personal environment: `geckograph validate --env personal --id <id>` (the feature id relearn printed, or `list_features`). A feature that calls a route only your local code has runs through the `geckograph dev` tunnel to your running app; when the tunnel is not open, validate stops and says to start it (`geckograph dev --start`). On the test account a person authorized for the tenant it sends real writes without asking again; say so in one line. The feature is proven when it passes two validations in a row. On a failure the fault may be in your new code or in its line: fix it, rebuild and restart the running app, run `geckograph relearn`, and validate again.
5. Reread the branch diff (see Before the commit).
6. Ask the person. Commit the code and the `geckograph.yml` diff only after they agree.
7. Do not try to change Staging or Live. Open the pull request: that is the last step here.

### Update a feature
- Change fields, path, or method by editing the line in place. To rename, edit `name:`.
- Editing a line's fields (added, removed, required or optional), binding or `name:` updates its action on your personal environment: relearn prints `Updated action: …`. A line that did not change is left alone.
- A new path with the same `name:` moves the action this personal environment created. A new path with another name is a new route: relearn creates its action and retires the old one if this environment created it.
- To change an endpoint Live already serves, leave its `source: dashboard` line alone. Add a code line for that route matching what it does now, run `geckograph relearn` (it records the line and changes nothing), then change the code and that line together. Staging and Live keep what they use until their state lets a new version in (`environments.md` beside this skill).
- Relearn never rewrites a login action, or an action it did not build whose request is not plain JSON: it prints `Not updated: <reason>`. Tell the person.
- A new method on the same path is a possible rename: relearn keeps the old action, creates none for the new line, and prints `Possible rename`. Tell the person.
- Then follow Add, steps 3 to 7 (rebuild the running app, relearn, then validate the changed feature on your personal environment).

### Remove a feature
1. Delete the procedure and the route's line: your `source: code` line, or its `source: dashboard` line when the route came from Live. Deleting the line is the removal: it is how the removal reaches the release and the shared environments. Do not suppress or hide the tool instead: neither reaches a release.
2. Run `geckograph relearn`. It retires the action (`Removed action: …`) when this personal environment created it, or when its route was an imported line the file no longer has, and hides a feature left with no active action (`Hidden feature: …`), which the agent no longer offers. A file with no line left retires nothing. Relearn does this for every line missing from the file, deleted on purpose or not: when it prints `Removed action` for a line you did not mean to remove, put the line back and run `geckograph relearn` again, and tell the person.
3. An action from Live that no line ever listed (a scan added it after the file's import) stays: relearn lists it as `in Live but not in geckograph.yml` and prints a dashboard link. Tell the person to open it, select the tool, and choose Suppress. Then follow Add, steps 5 to 7. `geckograph release` lists what it removed; when it prints `WARNING: still on in this release`, a route you meant to remove still has its line: delete it, relearn and release again.

### Repair a failing feature, or a rescan flag
The app worked when it was scanned: GeckoGraph captured each tool from a request the app's own screen sent and the app accepted. So a listed failure is GeckoGraph's to fix, in the graph or the tool, not in the app's code. If, while comparing, you find the app answering wrongly to its own screen's request, report it to the person (see `repair.md`, Never). `repair.md` beside this skill has the details.
1. List: `geckograph list_validation_failures --env <env>` and `geckograph list_scan_flags --env <env>`.
2. Read one: `geckograph show_validation_failure --id <id> --env <env>` (the outcome and every call the test made) and `geckograph show_tool --tool <name> --env <env>` (the request the app's screen sent in the scan, and its answer).
3. Find the difference between what our tool sent and what the screen sent. That difference is the fault. Work from the tool calls the run recorded (`show_validation_failure` lists them), not from the explanation's wording: a name it marks as not a tool in this version was never called. When the failure is older than the feature's current tools, or names such a tool, validate the feature again first and work from the new result. Then read the code behind the feature's routes in this repo (handler, permission checks, the data it needs) to confirm the real cause, and cite it (file:line) in your report. Act on what it shows: fix the graph (an input source, or a rule such as "changing a record someone else created needs approval", so the agent tells the user instead of failing); or say exactly which test data or account permission is missing, and where in the app to add it; or recommend switching the feature off. Never change that code to make a validation pass.
4. Fix it on your personal environment: one `geckograph edit_feature --env personal --input '{…}'` (a scanned tool's inputs: kind `tool_input`; the ids `<env>` printed work there too), `geckograph content --env personal`, or a switch-off (kind `suppress`, with the reason). Each edit is recorded. When `geckograph dev` says your personal copy is older than what `<env>` serves, run `geckograph dev --latest --from <env>` first (your local edits come along). A tool built from `geckograph.yml` is fixed on its line instead: `geckograph relearn` (with `geckograph dev` running), steps 5 and 6, then `geckograph check --tools <n>` and `geckograph release --base <n>`: release refuses a line your personal environment has not relearned.
5. Prove it there: `geckograph validate --env personal --id <id>`, then try it in the local widget, which shows your personal environment and its local edits. On the test account a person authorized in the dashboard it sends real writes without asking again (say so in one line); writes go only through that sign-in, a test tenant's. When validate says the test account couldn't sign in, give the person the dashboard link it prints: only a person signs it in again and ticks the test-tenant authorization. When rescan refuses because the account isn't marked as a test account, give the person the link it prints: only a person ticks the test-tenant authorization, in the Rescan dialog.
6. A feature is repaired when it passes two validations in a row with the same fix. Stop when the same failure comes back with the same evidence, or after 50 steps on one feature. Then run `geckograph promote --env <env>`: it sends your recorded edits to `<env>`'s draft. Pass on what it skipped and why, validate each promoted feature once on `<env>` with the command it prints (the draft's save needs that pass), and tell the person which features passed and which did not, and that the draft is theirs to save in the dashboard (a switch-off takes effect only then). Promote sends only features with two passes on your personal environment (a switch-off needs none) and lists the others as not proven; they stay there. When your local app cannot prove one (missing test data, say), repair that one on `<env>`'s draft directly (`--env <env>`) and say why. A `geckograph.yml` line goes through `check` and `release` instead. Once saved, the environment serves the draft to pages that send its tools number; never propose a deploy or repeating the edits elsewhere.

## What relearn does
- Reads the `source: code` lines of `geckograph.yml`. A dashboard line never creates an action. With only dashboard lines it prints `No code lines to relearn`.
- Creates, updates and retires actions on your personal environment only. It never changes Live or Staging.
- Without `geckograph.yml` it refuses: run `geckograph init` first.
- Makes each new line's action the tool of a feature in the area its path names. When no area matches, it adds one named after the path's resource (`/api/reports/monthly` -> Reports) and prints `New feature area: <area>`. Each link prints `Feature: <feature> (<area>) uses <action>`. An action it created earlier that is no feature's tool is linked on the next relearn; `No feature: <reason>` when it could not be.
- Prints what it did: `Applied N new endpoints`, `Updated action`, `New feature area`, `Feature`, `Removed action`, `Hidden feature`, `Not created`, `Not updated` or `No feature: <reason>`, name notes, possible renames, and actions from Live that the file does not list.
- If relearn prints `TIMEOUT` (also after a 502, 503 or 504), the server may still be applying the change. Do not edit `geckograph.yml`; wait a minute and run the same command again. If it applies nothing, the first run finished: the dashboard shows what changed. A retry of `geckograph relearn` while that job is still running attaches and prints its report. A retry after the job is done starts another one.

## Before the commit

Reread the branch diff (`git diff <base>...HEAD` plus uncommitted changes) and confirm every route the branch created, changed (method, path, or parameters) or removed is reflected in `geckograph.yml`: a new route has its line, a changed route's line matches it, a removed route's line is gone. This is a review you do, not a command. A route the branch added that the agent should not call (login, auth, chat, admin, webhooks) goes under `ignore:`; do not add lines for routes the branch did not touch. Check each new line against `surfaces:`: keep it only when code in a listed surface calls the route. Relearn refuses a file with an unknown `binding`, a path that names a host, or an `ignore:` entry that is not `METHOD /path`, and names each line.

## After the pull request
Stop at the pull request. There is no deploy command and no CI step: deploying the app with the committed tools number is what ships the release, and an environment that follows the code moves with the build on its own. Never tell the person a release needs a dashboard step, unless Approval is on and an internal environment waits for it; only holding, approving and rolling back are theirs, in the GeckoGraph dashboard.
